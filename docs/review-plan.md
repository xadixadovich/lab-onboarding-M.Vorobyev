## 3. Критерии проверки (чек-лист)
### 3.1. Функциональная корректность
- [ ] Результаты запросов совпадают с контрольными значениями на тестовых данных.
- [ ] Фильтрация и сортировка работают правильно.
- [ ] Тип JOIN выбран верно, а повторяющиеся значения в ключах не дублируют строки.
- [ ] Значения NULL и дубликаты учитываются верно и не искажают итоги.
- [ ] Границы периодов и часовые пояса в отчётах по датам указаны верно.
### 3.2. Безопасность
- [ ] Если запросы вызываются из приложения, значения в них передаются через параметры.
- [ ] У пользователя отчётов есть права только на чтение данных.
- [ ] Нет прямой подстановки непроверенных данных в SQL-запросы.
### 3.3. Производительность
- [ ] Каждый запрос выполняется не дольше 5 секунд на объёме данных, близком к рабочему.
- [ ] Одни и те же данные не вычисляются несколько раз.
- [ ] По плану выполнения запроса видно, что большие таблицы не читаются целиком и используются подходящие индексы.
- [ ] Запросы проверены на миллионах строк, время выполнения остаётся приемлемым.
- [ ] Не используется SELECT *, выбираются только нужные столбцы.
### 3.4. Читаемость и стиль
- [ ] SQL-запросы имеют понятную структуру.
- [ ] Названия таблиц и полей понятны.
- [ ] В коде нет лишних и повторяющихся частей.
- [ ] Код соответствует принятому стилю SQL.

## 8. Разрешение споров и эскалация
### 8.1. Правило «Двух голосов»
- **Если два рецензента не согласны друг с другом, они должны объяснить свою точку зрения и обсудить проблему.**
- **Если они не могут прийти к общему решению, последнее слово остается за тимлидом.**
- **Автор кода должен внести изменения, если они были согласованы с тимлидом.**
### 8.2. Эскалация
- **Если возник спор по поводу критической уязвимости безопасности, нужно обратиться к специалисту по информационной безопасности (CISO).**
- **Если спор касается архитектуры или переполнения памяти, решение принимает тимлид или главный архитектор.**
- **Пока серьезная проблема не решена, код нельзя добавлять в основную ветку проекта.**
### 8.3. Время на дискуссию
- **На обсуждение одного спорного комментария в GitHub PR дается 30 минут.**
- **Если за это время участники не договорились, они обращаются к тимлиду и обсуждают вопрос на встрече.**
- **Если проблема серьезная, например связана с безопасностью, нужно сразу обратиться к ответственному специалисту, не дожидаясь окончания 30 минут.**
